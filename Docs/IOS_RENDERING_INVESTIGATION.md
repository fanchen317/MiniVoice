# iOS 样式切换与音乐墙滑动排查（2026-10-29）

## 录屏证据与判断边界

用户录屏长15.55秒，1320×2868，声明帧率60。按每秒2帧抽样检查：样式切换附近出现两条横贯侧栏与背后页面的细线；快速滑动段多次出现封面区域空底、文字仍在。录屏的编码帧率不等于应用渲染帧率，不能从此计算或承诺应用FPS。

横线跨越独立组件边界，因此不符合单个按钮/侧栏描边问题。原切换链路执行 WKWebView.takeSnapshot → JPEG编码/base64桥接 → 解码 → 多块canvas裁图 → 逐块动画。整屏截图与分片合成是本轮移除的可疑路径；没有WebKit GPU跟踪证据，尚不能把特定系统缺陷认定为唯一根因。

抽帧记录保留于 `.build/reports/ios/render-investigation/`，不把用户原始视频加入仓库。

## 实施

1. iOS适配器选择`live`样式过渡：当前页面100ms淡出至0.35，提交目标样式并等待布局，再180ms恢复。使用一个真实页面的opacity动画，零截图请求、零JPEG编解码、零分片canvas。Android/Mac既有碎片动效保留。旋转、减弱动态、失败均清理动画；快速切换仍以最新目标为准。iOS宿主旧captureStyle入口返回空，避免旧调用再次触发读回。
2. iOS音乐墙挂载窗口提前360 CSS px，超过140px相机重定位阈值。原未聚焦overscan只有100px，小于阈值，连续滑动会在刷新前露出尚未挂载的区域。范围保持有限，不挂载整库。
3. 可见集合、封面React节点与逐卡投影按相机窗口/布局状态更新，普通播放位置轮询不再重建集合、重写每张封面的样式。纯平移沿用一个容器transform；缩放、聚焦、展开仍进行必要的逐卡布局。
4. iOS授权资源读取增加32MiB成本预算、192条数量预算的NSCache编码图片缓存（预算由系统管理，不是硬内存上限）；每次请求先校验歌曲和当前文件夹身份，目录更新清空缓存，原图请求不进入该缓存。版本化资源允许短期私有缓存，避免滚出/滚回时反复磁盘读取与授权解析。缓存不保存解码后的整库位图，系统可回收。

## 后续纠正：保留碎片效果，改用原生滚动（2026-10-29）

用户反馈上一轮滑动仍卡顿，并明确要求保留碎片切换。上一轮`live`淡入淡出方案撤回，不能再作为当前实现描述。

- **原动效**：`fragmentSamples`统一生成17个采样点，Android Web Animations与iOS Core Animation使用相同位移、卷曲、旋转、缩放、透明度、480ms时长与最多200ms径向延迟。iOS通过UIView区域快照视图准备最多24块，再由原生合成层动画，不做WKWebView整屏takeSnapshot/JPEG/base64/JS解码。原生碎片不可交互，旋转/减弱动态/过时token取消清理，3秒超时清理防止残留。未改为另一种视觉效果。
- **滑动链路**：iOS一指拖动、惯性改为WebKit原生双轴overflow滚动，JS仅同步相机并按需更新有限的封面窗口。画布使用空白滚动空间提供可滚动坐标，不挂载全部歌曲；靠近边界时重定位保持无限墙相机连续。扩大空坐标范围减少快速惯性期间触及重定位边缘；同步相机时禁止重写相同scrollTop/scrollLeft，避免打断原生惯性。
- **触摸规则**：发现封面自己的`touch-action:none`也会阻止父容器原生滚动，已修正。双指触摸开始时才注册阻塞touchmove监听和取消默认行为，按原墙面锚点缩放；一指平移没有阻塞touchmove监听。滑块保留自身手势，弹窗/全屏播放器期间禁用背景滚动。
- **图层**：原生滚动模式不强行把整个提前挂载区域提升为单张大纹理，由滚动背板处理；海报仍有限挂载、版本缓存和时钟轮询隔离。焦点/展开/收起与原生滚动坐标对应，旧相机状态仍可保存回读。

验证：112文件门禁；47项JS；共享墙面与Mac实际页面回归。Chromium真实touch输入验证一指原生滚动、双指只缩放墙面（document scale=1）、正反滑动及边界重定位可见ID完整，碎片动画没有被替换。真实WKWebView中三次切换均收到原生prepare/animate，并验证滚动相机、封面加载与完整宿主回归。原生XCTest使用系统合成手指连续拖动，再实际点按品牌按钮循环三样式，第二轮通过；初轮因测试把自有选择控件当成Button而查找失败，改用其真实Switch语义。

原生测试完整xcresult及截图：`.build/reports/ios/native-pan-xctest2.xcresult`、`native-pan-attachments/`。另录制专用模拟器真实点按视频并以8帧/秒抽样，确认中间帧确有碎片卷曲/散开、结束无残留；文件 `.build/reports/ios/native-fragment-motion/run.mp4` 与contact.jpg。截图/录屏与模拟器用例不能证明用户实体设备的GPU帧率或横线已在所有系统版本消失，仍保留真机验收边界。

## 后续：点击聚焦、双击播放、侧栏深度的开销（2026-10-29）

用户确认原生滚动明显改善，但点击变方形、双击播放和侧栏开合仍卡顿。本轮继续保留原生滚动与碎片切换，只优化这些交互的执行路径。

### 发现与实施

- 原聚焦每帧修改周围海报width/height，并反复进行object-fit裁图和文字布局。iOS改为固定最终布局盒，预采样33点transform/opacity轨迹，由Web Animations合成。图片按原始宽高比计算cover尺寸，并用子层反向缩放抵消父层变形；文字同样反向缩放，避免封面/歌词拉伸。动画期间JS只跟踪用于打断和保存的进度/相机，不逐帧改写海报尺寸；结束回到原有真实几何。图片解码导致的visibility变化不能被动画清理覆盖，因此只恢复动画自己修改的样式属性。
- 聚焦期间先使用已缓存缩略图，动画完成后再交接高清封面，避免在变形中同时引入大图解码/上传。快速重选、双击和侧栏中断从当前进度续接；侧栏关闭后完成被中断的聚焦，不停在半成形状态。
- 原侧栏深度每帧重投影整片墙并改变所有海报尺寸。iOS现在对同一个原生滚动表面作320ms scale(.92)过渡，保留全幅墙面的提前挂载采样，工具栏仍独立；侧栏开合不再改写每张封面的宽高。Android旧投影路径保留。
- 双击播放更新recent时，音乐库页面也会重新排序；比较器每次localeCompare还携带locale/options。目录依赖现在仅包含当前分组需要的recent/favorites/playlist，排序复用Intl.Collator，空查询不再拼接并规范化全部歌曲信息。数字标题、全角查询及非破坏排序有回归断言。

### 可复核数据与范围

本机Electron、440×956窗口、1037首合成目录，同一测试在a8300b8的Wall基线与新实现对比：聚焦约100–330ms采样段海报尺寸变更记录1036→0；侧栏约70–250ms段2142→0。不是“整段动画零布局”，起止会设置真实尺寸。数据存于 `.build/reports/ios/focus-motion/{baseline,optimized}.json`，脚本 `Scripts/tests/test-ios-focus-motion.cjs`；这些是DOM开销记录，不是用户设备FPS。

同机Node、相同1037首随机数字标题、8次目录调用，排序前后ID严格一致：原18.28–21.02ms，新0.84–1.08ms，记录 `focus-motion/catalog-profile.json`。这说明比较器与查询处理的CPU开销减少，不是WebKit/GPU帧率测量。
