# 移动点击响应审查（2026-11-06）

本轮只读代码审查；未量测真实iOS/Android输入到显示延迟，不将风险直接称作实机根因。

## 共享链路
- state.js的reduce等待core和write完成才更新controller state，且所有动作共享串行队列：存储/桥接延迟会推迟界面提交，连续点击会排队。优先将可逆界面状态即时反馈与持久化分离，仍需版本/失败回滚防止旧操作覆盖新操作。
- PortablePlayer的播放/切歌等等待宿主后refresh，部分导航含多个await patch/reduce；不同按钮反馈时点不一致。应逐入口分类：即时局部状态、异步业务忙碌、后台任务，不能统一禁用所有按钮。
- ActionButton同时处理pointer/touch/click，touchEnd合成点击并阻止兼容点击；需要保留防鬼点机制，重点在WKWebView/WebView验证单次触发与滚动取消，不能简单删除事件路径。
- ActionButton在pointerUp读取computedStyle并启动380ms弹簧，即使触摸随后因移动取消也可能先产生松手反馈。需区分合法点击与滚动结束；固定380ms还会让快速连续触发显得拖沓。
- PortablePlayer持有播放snapshot/position等顶层状态，stableSongs逐条JSON.stringify比较；大曲库下重复比较、顶层重渲染会与触摸争抢主线程。建议独立时钟store、基于catalog revision的对象复用与页面selector。
- useSurfaceMotion关闭时cloneNode整个面板、读取几何/样式并创建退出层；大侧栏/列表弹窗的关闭可能产生同步开销。应保留节点退出或仅为必要表面建立有界过渡，保持焦点/返回/快速重开规则。
- 样式切换需等待截图/解码/状态flush，且680ms碎片过渡：预期的视觉效果不应当作为每个按钮的完成等待。保持最新意图合并，减少串行持久化。
- 多层CSS/WAAPI同时反馈，主按钮、滑块、搜索及墙手势应分别规定唯一动画所有者；不可用更短动画掩盖主线程任务。

## iOS
- WKWebView桥经messageHandlers后主线程分派/回传；host-fragments样式切换额外经过原生prepare/animate。要将输入、桥接、持久化、首帧分别埋点，不能以Chromium耗时代表WebKit。
- 实际检查TouchEnd cancelable、快速轻触/滚动接点击、边缘返回、软键盘及系统中断；无需假定所有点击都有300ms延迟。
- 同屏封面解码、歌词canvas、玻璃采样与原生截图并行时的内存/合成开销需专用模拟器和实体机验证。

## Android
- 宿主桥的worker请求、JSON/快照与UI线程回传需记录排队时间；区分播放交互和扫描/文件任务是否争用队列，再决定分级调度。
- 验证不同WebView/低配设备的触摸取消、Pointer捕获与兼容点击；已有防重路径不能凭桌面鼠标测试判定可靠。
- 重点测试扫描期间播放/收藏/导航、前后台恢复、蓝牙切换；音频focus行为是另一条业务链路，不能归因于按钮动画。

## 建议实施顺序
1. 加分段耗时与单次激活计数，构建合成曲库交互基准（点击首反馈、业务完成、下一帧）。
2. 可逆界面状态不等待落盘；保存队列合并并保留错误反馈/版本校验。
3. 播放时钟与大曲库状态拆分，减少每次更新的序列化/渲染。
4. ActionButton合法触摸反馈与快速重入统一；减少大型退出clone。
5. iOS/Android真机连续操作对照，按实际长任务结果优化图片/玻璃/画布。
