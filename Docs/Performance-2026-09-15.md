# MiniVoice 性能检查与优化（2026-09-15）

## 已解决的主要热点

- 原列表在视图刷新时多次筛选和排序，排序比较器还逐次查询磁盘修改日期。现在后台 actor 处理排序，日期每首歌曲每个音乐库版本最多读取一次，界面仅在歌曲、搜索、排序或最近播放变化时更新列表快照。刷新时清除 Foundation 自身的日期缓存，避免旧日期影响顺序。
- 原播放进度每 0.2 秒发布到整个 MusicLibrary，牵连列表和背景刷新。现在 PlaybackClock 独立发布，进度控件和歌词单独订阅。
- 歌词改成按需解析缓存，编辑后失效；歌词高亮每次视图计算只查找一次当前行。桌面歌词关闭时不计算，文本未变时不重复发布。
- 封面背景取色增加容量为 8 的缓存，避免相同封面重复转换 TIFF 并采样颜色。
- 当前歌曲和最近歌曲通过字典查找，跨目录扫描复用通过路径索引查找，消除反复线性扫描。
- 大歌单缓存恢复每 64 首让出主线程，降低长批次连续占用主线程的风险。
- 系统音量轮询只在实际值变化时发布，避免不变的设备、音量信息反复刷新控件。

## 验证

- 使用 Xcode 工具链运行 `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test`：18 项测试全部通过。
- 新增测试覆盖自然排序、升降序、歌手/专辑搜索、最近播放顺序、修改日期缓存失效、歌词缓存与编辑副本隔离，以及 100 次播放进度更新不会发布 MusicLibrary 变更。
- 10,000 条合成歌曲（倒序标题）单次标题排序约 5.9 毫秒，debug 构建。本项是特定数据的微基准，不代表完整启动时间或滚动帧率。
- Release 构建及 codesign 校验通过，已通过部署脚本替换 `/Applications/MiniVoice.app` 并重启。
- 实际缓存歌单：1,042 首，缓存约 14.86 MiB；启动后歌曲计数正确，播放进度正常前进，播放中滚动能显示后续歌曲。
- 旧版和新版各采样 3 秒。旧版调用树出现反复 `ContentView.songs`、`ContentView.compare` 和 `LRCParser.parse`；新版播放采样未出现这些热点。原始采样保存在同目录 `before.sample.txt` 和 `after.sample.txt`。
- 两次采样的进程运行时长、编辑状态不同，因此不将内存差异作为受控性能提升，也未测量完整冷启动耗时或滚动 FPS。

## 仍可继续分析的路径

手动完整扫描仍逐个调用 ffprobe/ffmpeg；音频首次 prepareToPlay、完整封面生成歌单缩略图、删除时重写缓存仍有同步工作。全窗模糊、透明材质和歌词效果仍有 GPU 成本。本轮保留视觉设计，主要消除已由代码和运行采样确认的重复 CPU/磁盘工作；这些剩余路径需要对应操作的单独采样，不能据此认定所有可能卡顿均已消除。

当前工作区同时包含用户其他任务的播放交互与界面改动；均予以保留，没有提交 git commit。
