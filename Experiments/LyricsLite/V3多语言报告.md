# V3 多语言适配报告

日期：2026-10-19。独立实验原型，未替换正式AI；用户歌曲、歌词和元数据未修改。

## 本轮实现

1. 语言感知的字符处理：繁简转换只用于中文，日文汉字保留；NFKC处理兼容字符、半角假名和韩文组合，保留重音和印度文字元音符号。
2. 先重组跨token的完整Unicode字素，再进行文本匹配，修复分离重音、元音标记等被丢弃的问题。
3. 支持auto及常见语言区域标记。高置信歌词语言作为识别提示，无法判断时由音频选语；每次输出记录语言选择诊断。
4. 同时使用局部语种窗口和跨语言上下文；原生强制对齐逐窗口选择语言，保留中英混唱上下文。
5. 对概率较低的候选，额外要求更强的独立识别支持。同样歌词仅换裁剪边界不再计为两份独立文本上下文。

实验模型与运行程序约 **190.6 MiB**。使用系统NaturalLanguage框架选语，没有增加打包模型；仍不依赖Python/PyTorch运行环境。

## 真实日文歌唱

使用本地《Butter-Fly》65秒片段，显式ja与auto均匹配7/7行。相对现有LRC的中位偏差0.87秒、最大6.44秒。正式stable-ts基线也与该LRC有多秒偏差；V3和正式基线的起点差异中位0.44秒、最大2.14秒。因此这份参考LRC存在质量疑点，需人工听音核对，不能据此宣称日文演唱对齐已达标。

## 验证与限制

- 20项原生匹配/语言回归检查通过，覆盖脚本、组合字符、语言别名、重复句和空结果。
- 静音、完全无关歌词、日文演唱配不相干中文歌词3种负例，各3行均未产生时间。
- 8种合成语音均检查输出原文未改变。
- 现有正式AI保留。当前轻量原型仍未达到全语言歌曲可替换标准。
- 继续沿用现有LRC参考，没有人工逐句标注；正式基线CPU和原型Metal后端不同；单轮耗时不能当作公平速度排名。
- 爱情转移源文件解码存在FLAC帧警告，参考结果保留此前样本质量限制。
- 语言代码被推理库认识，不意味着small模型含相应专用token；原生对齐器校验实际模型token范围。

## 使用

参见README。多语言测试命令：`python3 Experiments/LyricsLite/multilingual_tests.py`。每次请求输出旁的diagnostics.json记录请求语种、模型语种和各语种窗口数量。下一步需要人工核对的多语言歌唱验收集，再针对弱语种和长曲漏行改进；不据合成语音结果直接扩大正式支持承诺。
